How to read evidence

Use the same mental flow for IEC-101, IEC-103, and IEC-104.

Start with connection state, then verify addressing, then verify startup data, then inspect command confirmation, events, quality flags, and timing. ARIEC60870 keeps the raw proof visible while explaining selected frames and summarizing findings.

1. Is the link/session alive?For IEC-101/103, check serial and link-layer responses. For IEC-104, check TCP, STARTDT, TESTFR, and sequence behavior.
2. Is the address correct?Separate link address from ASDU Common Address. A device can answer while application data uses the wrong CA.
3. Did startup complete?General Interrogation should provide a clear startup snapshot. Missing ACTCON, termination, or values are evidence.
4. Can the evidence be reported?Use raw frames, decoded values, events, Smart Findings, and PDF report output together.

IEC-101 fundamentals

Serial RTU links often fail in the small details: bits, classes, addresses, and GI flow.

IEC-101 troubleshooting is not only about whether the port is open. The useful clues are often ACD/DFC bits, polling strategy, Common Address, IOA mapping, and command confirmation.

ACD and DFC

ACD means the outstation has Class 1 data waiting. DFC means data flow control: the device is temporarily busy. If these bits are ignored, the master may poll the wrong class or overload the link.

Read ACD/DFC guide

Class 1 and Class 2 polling

Class 2 is normal cyclic/background data. Class 1 is high-priority event or confirmation data. A healthy master does not hammer Class 1 forever; it drains it when the slave signals demand.

Read polling guide

Common Address vs Link Address

The link address selects the station at link layer. The Common Address identifies the ASDU/application station. A CA mismatch can look like a connected device that still provides wrong or missing application data.

Read addressing guide

General Interrogation

GI is the startup snapshot. A useful trace should show activation, confirmation, returned data, and completion/termination behavior. If GI is incomplete, the report should show which proof is missing.

Read GI guide

Command flow

A command is not proven by TX alone. Look for select/execute behavior, ACTCON, process feedback, ACTTERM, quality, and timeout evidence.

Read command guide

IEC-104 essentials

TCP connected is not the same as protocol healthy.

IEC-104 adds APCI session control, U-frames, I/S-frame counters, and keepalive behavior. A device can be reachable over TCP while data exchange is not usable.

STARTDT / STOPDT / TESTFR

STARTDT enables data transfer, STOPDT stops it, and TESTFR checks liveness. Missing confirmations should be treated as protocol evidence, not only a generic timeout.

Read IEC-104 session guide

I-frame, S-frame, U-frame

I-frames carry ASDUs, S-frames acknowledge receive sequence, and U-frames control the session. Sequence issues are easier to explain when frame counters are kept near the raw trace.

Read sequence issue guide

IEC-104 troubleshooting

When TCP is open but values do not move, check STARTDT, GI, CA, sequence counters, TESTFR, and whether the outstation actually sends expected ASDUs.

Troubleshooting cookbook

When something looks wrong, start from symptom, proof, and next step.

These pages are designed for search intent: the exact problems engineers type when a device connects but does not behave correctly.

Common Address mismatch

Device answers, but ASDU CA is not the configured project CA. This can make values appear missing, wrong, or unrelated.

Read CA guide

GI incomplete

GI starts but does not produce a full usable startup snapshot. The evidence should show whether confirmation, data, or termination is missing.

Read GI issue guide

ACTCON missing

Command TX is not enough. Missing activation confirmation, feedback, or termination should be tied to the exact frame proof.
