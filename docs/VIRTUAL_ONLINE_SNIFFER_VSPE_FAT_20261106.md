# Windows bench guide — VSPE + Virtual Online Sniffer acceptance

**Date:** 2026-11-06  
**Status:** **Proposed test plan, NOT a currently supported ARIEC60870 feature and NOT an executed test.**  
**PRD:** [Virtual Online Sniffer requirements](VIRTUAL_ONLINE_SNIFFER_PRD_20261106.md)  
**ARD:** [Virtual relay design](VIRTUAL_ONLINE_SNIFFER_ARD_20261106.md)

## 1. Prerequisites and topology

Use licensed/installed VSPE compatible with Windows. The user's existing VSPE installation is sufficient **if** it can create two independent `Pair` devices. Neither ARIEC60870 nor this repo installs any driver or creates COM ports automatically.

| VSPE device | Virtual Pair ends | Application COM owner | ARIEC relay COM |
|---|---|---|---|
| Pair A | COM11 ↔ COM12 | IEC Master -> COM11 | Master-side -> COM12 |
| Pair B | COM13 ↔ COM14 | IEC Slave -> COM14 | Slave-side -> COM13 |

**Do not create one Pair COM11↔COM14 and attempt to open these same endpoints again in ARIEC60870.** Each ordinary COM handle has a clear owner. If ports conflict with existing COM devices, use any four distinct free numbers and update the mapping.

    Master COM11 <-> VSPE Pair A <-> COM12 [ARIEC inline relay] COM13 <-> VSPE Pair B <-> COM14 Slave

In VSPE: `Device -> Create -> Pair` (twice); use one lane per pair, keep any setting that allows silent `Allow buffer overruns` OFF for integrity testing; do not enable an option that reports successful writes when the other side is absent if doing fidelity verification. Verify pair readiness/driver support and save the VSPE configuration separately. Do not assume `Emulate baud rate` enforces real physical serial timing.

## 2. External programs and future ARIEC setup

- Master: connect to COM11.
- Slave: listen on COM14.
- **Future** ARIEC60870 mode: `IEC-101 Virtual Online Sniffer`, Master-side relay COM12, Slave-side relay COM13.
- Set matching supported UART profile in all apps, e.g. 1200 bps 8E1 for an interoperability case; check every app's actual settings. Use no hardware RTS/CTS handshake for V1.
- Match link address width / COT / CA / IOA choices **only for correct decoding**; forwarding must not depend on these widths.
- In future ARIEC, select `Start Relay` and ensure `COMs open; peer not verified` is initially distinguished from real observed traffic. Then connect Master and Slave, issue a benign link-status/poll/GI through the **external Master**, and inspect both original HEX streams. ARIEC must not originate polling or E5 itself.

**Current master has no Virtual Online Sniffer relay mode.** Its existing `IEC-101 Passive Monitor` cannot be used as the middle of the chain to forward COM12↔COM13; do not mistake opening two RX-only taps for creating this relay.

## 3. Reproducible acceptance script (manual + future automated bench)

1. Start with **two** independent two-way terminal/mock applications and exchange fixed raw byte vectors through both pairs. Prove raw bidirectional byte equality before introducing protocol parsing.
2. Send Master->Slave bytes `00 E5 A2 FF 10 68` and additional arbitrary binary. Repeat reverse direction. Do not require valid FT1.2 framing to forward a byte.
3. Stream valid single-character E5, short `10 ... 16`, long `68 L L 68 ... CS 16`, intentionally invalid checksum, incomplete trailing fragment and back-to-back records in each direction. Capture both endpoint byte streams and the proposed relay ingress stream.
4. Use a test peer to fragment writes at 1 byte, 2 bytes and randomized boundaries; compare concatenated streams, never per-read chunk counts.
5. Verify under load and with frozen/slow GUI that the actual relay remains binary correct even when observation is partial. Any observation overflow must have explicit visible gap/error evidence.
6. Induce one COM busy/port-open failure, read/write timeout, peer shutdown, COM/VSPE device disappearance and Stop during traffic. Verify two-sided fault/cleanup and uncertain delivery. Never silently auto-replay a possibly delivered command.
7. Repeat open/stop/restart 100 times on a test machine with no stale direction or handle state.
8. Test `Emulate baud rate` OFF then ON, while recording driver option, throughput and latency. Do not extrapolate Windows host timestamps to UART bit edges.
9. Record test metadata, SHA-256 of both source sends and destination reads, byte counts and first mismatch offsets. Do not publish private customer data.

**Pass** only when each independently captured peer stream exactly matches its corresponding input stream, Stop/restart is deterministic and unknown/loss accounting is truthful for the measured scenario. Driver write success **alone** is not a pass.

## 5. Troubleshooting map (future operator messages)

| Symptom | Investigate |
|---|---|
| Master appears connected but 0 bytes ingress COM12 | Pair A ownership/mapping, peer writes, VSPE port status, absent peer |
| COM12 receives bytes but COM13 never completes writes | ARIEC relay egress path, COM13 open/timeout/buffer, Pair B |
| COM13 writes but Slave sees nothing | Pair B direction/port assignment, driver overrun options, Slave COM14 open/read |
| Slave responds but COM13 sees nothing | Reverse Pair B source, Slave COM14 configuration |
| Both directions have RX but 0 decoded IEC101 frames | Wrong UART/IEC field widths, malformed streams, decoder/frame boundary; **show original HEX anyway** |
| Relay stops after GUI HOLD/scroll | Bug: observation/UI pressure must not control forwarding |
| Application reports complete but bytes/hashes differ | FAIL: investigate silent VSPE buffer-overrun settings or unknown/incomplete forwarding, never hide discrepancy |
| 1200 bps selected but very fast data rate | VSPE might not emulate wire baud; check Pair option and distinguish simulated vs physical timing |
